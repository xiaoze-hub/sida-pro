# 数据落库与共享缓存设计（最大化落库 · 历史可查）

- **文档版本**: v1（2026-09-10）
- **基线**: main @ `e7e4e79`（v0.5.41）
- **诉求（老板）**: 市场/标的类数据**尽量落库**，这样**能查历史**；同时避免多账号同时访问同一数据时**各自打上游接口**。
- **非目标**: 不改多用户归属红线（M7 刚收口）；不把私有数据（持仓/自选/建议/报告）做成共享。

---

## 1. 一句话方案

**按"时效语义 × 归属"把数据分三层落位**：
- **L0 定稿历史 → PG/TimescaleDB**（可回测、可复盘、长期留）
- **L1 热数据 → Redis TTL**（跨 worker / 跨账号共享，替代进程内缓存）
- **L2 实时流 → 不落库**（秒级 tick、WS）

并把 PG 侧的**存储治理（hypertable + 压缩 + 保留 + 连续聚合）**作为前提——否则"最大化落库"会在数周内撑爆磁盘。

---

## 2. 现状盘点（实测，非推测）

| 项 | 事实 |
|---|---|
| 数据库 | PostgreSQL **16.15** + **TimescaleDB 2.29.2**（生产 `panwatch-postgres`），库总 **17 GB** |
| hypertable | **仅 `klines`** 一个（周分块，**未压缩**） |
| 最大表 | **`l2_ticks` 75,645,593 行 / 16 GB**，且是**普通表**（非 hypertable），范围仅 **2026-09-03 → 09-10（7 天）**≈ **2.3 GB/天** |
| Timescale 策略 | **只有** telemetry / job-history 两个内置 job；**无压缩、无保留策略** |
| Redis | 生产**已接通**（`redis://redis:6379/0`），但**只用于 streams**（`kline_backfill` 任务），**未做数据缓存** |
| 进程内缓存 | `packages/marketdata/.../client.py` 的 `TTLCache`：quote=5s、**kline=0s**、capital_flow=0s、board_flow=300s、… | 
| worker | `WEB_WORKERS=2` → **进程内缓存 per-worker**：同标的会被两个 worker 各拉一次，缓存互不可见 |
| 已有落库先例 | `klines`(117,514 行) / `news_cache` / `market_scan_snapshots` / `market_regime_snapshots` / `stock_universe_snapshots` / `strategy_factor_snapshots` / `auction_anomaly_records` / `seal_quality_samples` / `limit_up_events` |
| 磁盘缓存先例 | `disk_cache`（`dark_flow` / `chip_distribution` / `darkflow_alerts`），落 `/app/data`，**跨 worker 共享** |

**两个直接结论**：
1. **"各账号各打一次"的放大器是 worker 数**——进程内缓存 + 2 worker 必然重复打源；共享缓存必须出进程（Redis）或出内存（文件/PG）。
2. **"最大化落库"的真正瓶颈是存储**——`l2_ticks` 已证明逐笔级数据 7 天 16 GB。**没有压缩/保留策略之前，不要扩落库面**。

## 3. 分层模型

```
                    ┌──────────────────────────────────────────────┐
   前端/API 读 ───► │ L1 Redis (热, TTL 秒~分钟, 跨 worker/账号共享)  │
                    └───────────────┬──────────────────────────────┘
                                    │ 未命中
                                    ▼
                    ┌──────────────────────────────────────────────┐
   定稿/回测读 ───► │ L0 PG/TimescaleDB (定稿历史, 可回测/复盘/聚合) │
                    └───────────────┬──────────────────────────────┘
                                    │ 未命中/需最新
                                    ▼
                    ┌──────────────────────────────────────────────┐
                    │ 上游源 (TQ/thsdk/腾讯/东财/悟道/问小达)        │
                    └──────────────────────────────────────────────┘
        L2 实时流(tick/WS) 直连, 不经 L0/L1
```

写入者统一为**后台采集/调度**（scheduler/collector），API 层**只读**（避免请求路径写库、避免写放大与锁竞争）。

## 4. 落库矩阵（最大化落库的具体清单）

> 口径：**共享**=与账号无关的公共市场数据（key 不含 user_id）；**私有**=必须 user_id 隔离。
> 保留：`raw`=原始明细；`agg`=按需聚合。

| # | 数据集 | 现状取法 | 落点 | 粒度 / 键 | 写入者 | 保留 | 归属 |
|---|---|---|---|---|---|---|---|
| 1 | 日/周/月 K线（含复权） | marketdata kline TTL=0，**每次打源** | **L0 `klines`**（已是 hypertable） | `(symbol,market,period,adjust,ts)` | 盘后 scheduler + 增量补 | 长期（压缩） | 共享 |
| 2 | 分钟 K线（1/5/15/30/60） | 同上 | **L0 `klines`**（新增 period 值） | 同上 | 盘中滚动写 + 盘后定稿 | 90 天 raw → agg | 共享 |
| 3 | 快照行情（现价/涨跌/量比/内外盘） | 进程内 5s | **L1 Redis**（主） + **L0 `quote_snapshots`**（**仅自选∪持仓 ∪ 指数**，1min 桶） | `quote:{market}:{symbol}` / `(symbol,ts)` | 已有聚合器/采集器 | L0：1 年 → agg 日线 | 共享（标的公开） |
| 4 | 资金流（个股/大盘/板块） | capital_flow=0s 直取 | **L1 Redis 300s** + **L0 `capital_flow_daily`/`*_intraday`** | `(symbol/market,ts)` | 采集器 | 日频长期；分时 90 天 | 共享 |
| 5 | L2 盘口/逐笔 tick | 直取 | **L0 `l2_ticks`（转 hypertable + 压缩 + 保留）**；聚合结果入 `*_daily` | `(symbol,ts)` | 采集器 | **raw 30–90 天 → 聚合长期** | 共享 |
| 6 | 集合竞价（TQ/thsdk/悟道） | 请求内直取 | **L1 Redis 30–60s** + **L0 `auction_snapshots`（当日唯一，必落）** | `(symbol,trade_date)` | `auction_review`/采集器 | 长期（数据量小、复盘价值高） | 共享 |
| 7 | 板块/题材/主线 | 部分落库 | **L0 `board_daily` / `market_regime_snapshots`(已有)** | `(board,ts)` | 盘后 job | 长期 | 共享 |
| 8 | 涨停/连板/炸板/封单成色 | 部分落库（`limit_up_events`/`seal_quality_samples` 已有） | **L0 保持 + 统一 ts 口径** | `(symbol,ts)` | 盘中采样 + 盘后定稿 | 长期 | 共享 |
| 9 | 筹码分布（成本峰/获利盘） | `disk_cache` | **L0 `chip_daily`**（每日一算一存） | `(symbol,trade_date)` | 盘后 job | 长期 | 共享 |
| 10 | 新闻/公告/事件 | `news_cache` 已有 | **L0 保持**（补 `symbols` 索引 + 去重键） | `(source,external_id)` | 采集器 | 90 天 → 主题聚合 | 共享 |
| 11 | 异动池/机会池/扫描快照 | `market_scan_snapshots` 等已有 | **L0 保持**，补 `trade_date` 分区索引 | `(snapshot_date,symbol)` | 扫描 job | 长期 | 共享 |
| 12 | 因子/策略/预测结果 | 已落库 | **L0 不动**（`strategy_factor_snapshots` 等） | — | 引擎 | 长期 | 共享 |
| 13 | 持仓/自选/账户/建议/报告/通知 | PG，user_id 隔离 | **L0 不动（私有）** | `user_id` 必带 | 业务 | 业务口径 | **私有** |
| 14 | 实时 WS 推送流 | 内存/Redis streams | **L2 不落库**（Redis TTL ≤ 5s） | — | 聚合器 | — | 共享 |

**"最大化落库"的取舍点**（必须明确，否则不可持续）：
- **全市场 × 5s 快照**：5000 标的 × 12 次/分 ≈ **6 万行/分 ≈ 8600 万行/天** → **不落 PG**；只落**自选∪持仓∪指数**的 1min 桶，其余走 Redis。
- **全市场逐笔 tick**：同 `l2_ticks` 现状（2.3 GB/天）→ **只对自选∪持仓**保留原始；全市场只保留**聚合**（分钟资金流/大单统计）。

## 5. 存储治理（前提，必须先做）

| 动作 | 对象 | 预期 |
|---|---|---|
| **转 hypertable** | `l2_ticks`（按 `ts`） | 支持按时间裁剪查询 + 后续压缩/保留 |
| **开启压缩** | `l2_ticks` / `klines` 历史 chunk | 时序数据通常 **5–10×**；16 GB → 约 2–3 GB |
| **保留策略** | `l2_ticks` raw 30–90 天；聚合表长期 | 增长可预测，不再线性撑爆 |
| **连续聚合** | 分钟 K线 → 日线；tick → 分钟资金流 | 查询走聚合表，快且省 |
| **分区/索引校准** | `quote_snapshots` 等新表按 `trade_date` 分区 | 历史查询按日期裁剪 |

> 现状风险：**TimescaleDB 已装但完全未用其治理能力**（无压缩/无保留），这是当前 16 GB 单表的最大成因。

## 6. Key 与隔离规范（红线）

1. **公共数据 key 一律不含 `user_id`**（`quote:CN:600519`、`kline:600519:1d:qfq`）。
2. **私有数据不得进共享缓存**；如需缓存，key 必须带 `u:{user_id}`，且 TTL 短。
3. **落库表的 `user_id` 语义**（沿用 M7）：`NULL` = 系统/遗留共享；有值 = 私有。**新建公共表不要用 `user_id` 列**。
4. **禁止把某人的自选拼进公共数据**（如"我的榜单"必须是私有视图，不能落成公共快照）。

---

## 7. 一致性与并发

- **缓存击穿**：热点 key 过期瞬间并发回源 → **单飞**（Redis `SETNX` 锁 或 进程内 asyncio 锁）。
- **缓存雪崩**：TTL 加 **±10% 抖动**；批量刷新错峰。
- **回填/修复**：所有 L0 表必须能用**同一采集函数**按 `(symbol, 日期区间)` 重放补数（幂等 upsert），否则历史不可修。
- **写库路径**：只在后台 job 写；API 层只读（避免请求路径写库、避免与 scheduler 抢锁）。
- **口径一致性**：写入时打 `source` + `quality_flag`（`klines` 已有此列）；读侧透传，不用"猜"。

---

## 8. 可观测与验收指标

- **命中率**：Redis `keyspace_hits/misses`；新表按 `trade_date` 查询的 rows_read。
- **上游调用量**：给 vendor 层打点（method/次数/延迟/来源），对比改造前后**每分钟出网请求数**（这是"少打源"的硬指标）。
- **落库量/体积**：每日新增行数与 GB（pg_stat_user_tables + pg_total_relation_size）。
- **门禁**：改造后**全量离线套件 + 冒烟 9/9** 不得下降；接口响应 P95 不劣化。

## 9. 分批落地路线

**批次 1：治存储 + 立共享缓存（收益最大、风险最低）**
1. `l2_ticks` 转 hypertable + 压缩策略 + 保留策略（先只加策略，不动代码）。
2. marketdata `TTLCache` → **Redis 后端**（接口不变）→ 一举消除"2 worker 各拉一次"。
3. 验收：出网请求数下降幅度、`l2_ticks` 体积不再线性增长、冒烟 9/9。

**批次 2：补落库面（历史可查）**
4. 新增 `auction_snapshots`（竞价，当日唯一）、`chip_daily`、`quote_snapshots`（自选∪持仓，1min）。
5. 分钟 K线入库 + 连续聚合到日线。
6. 验收：历史页/回测能从 L0 取到上述数据，不必回源。

**批次 3：查询侧收口**
7. 前端历史查询改走 L0（带日期区间的自上而下裁剪）。
8. 缓存命中率/出网量面板；按数据面给"新鲜度"标注（避免把旧值当实时）。

---

## 10. 风险与回滚

| 风险 | 缓解 | 回滚 |
|---|---|---|
| 压缩/保留策略误删历史 | 先 `compress_chunk` 单 chunk 试；保留策略先用 90 天宽阈值 | `decompress_chunk`；恢复备份 |
| Redis 不可用 | 降级为直读 L0/PG（**不得回退成"打上游"风暴**）；连接失败快速失败 | 关闭开关即回旧路径 |
| 写放大影响盘中 | 写入限速/批量 upsert；错峰在非交易时段跑重活 | 停对应 job |
| 历史口径与旧行不一致 | 打 `source`/`quality_flag`；文档标注"历史数字不可比" | 按 `source` 过滤重算 |
