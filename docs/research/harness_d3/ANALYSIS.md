# Harness D3 分析：内置智能体到底有没有用

评测对象：生产 v0.19.13，`admin` 账号，2026-10-20 01:2x（收盘后）。
6 个内置智能体 × 3 个真实问题 = 18 次；另跑 3 次**不指定智能体**作为基线。
原始数据：`runs.json`。

## 一、先看结论

1. **配方确实改变了行为**，但改变的不是"省工具"，而是**"在需要深挖的问题上挖得更深、并且守住纪律"**。
2. **原先"白名单会减少工具调用"的假设被证伪**：premarket 与 chip 的工具调用反而翻倍。
3. 首轮评测的"结构合规"指标本身是错的（只认 `【依据】`，而配方用的是 `隔夜事件/涨停结构/风险清单`），
   已在脚本里改成"按配方自己的 output_sections 判定"。**因此表里那一列不可用于结论**。

## 二、工具调用（stage 事件数）

| 智能体 | 3 问工具数 | 均值 | 基线 | 差异 |
|---|---|---|---|---|
| premarket_strategist | 7 / 3 / 10 | 6.7 | 3 | **+123%** |
| auction_hunter | 4 / 2 / 3 | 3.0 | — | — |
| intraday_watcher | 2 / 2 / 3 | 2.3 | — | — |
| postmarket_reviewer | 6 / 2 / 3 | 3.7 | 3 | +23% |
| risk_judge | 2 / 6 / 2 | 3.3 | 2 | +65% |
| chip_analyst | 3 / 5 / 4 | 4.0 | 2 | **+100%** |

读法：**盘前**要串隔夜事件 + 40 只自选 + 题材强度，**筹码**要 CYQ + 逐笔 + 盘口 + 技术面，
这两个场景默认配方只取 2–3 个工具就下结论，配方版多取一倍 —— 这是"补维度"，不是"瞎探查"。
防守类问题（`intraday_watcher` 2.3 次）仍然很省，说明白名单没有把简单问题复杂化。

## 三、内容层面的真实差异（人工抽读）

| 场景 | 默认配方 | 指定智能体 |
|---|---|---|
| 持仓风险 | 2 次工具 →「查不到你的持仓，把代码发我」（193 字） | 6 次工具 → 1227 字，逐只列破位/浮亏/纪律线 |
| 涨停梯队 | 3 次工具 →「0 家涨停，情绪温度 45」（410 字，直接引用系统信号） | 6 次工具 → 795 字，含梯队结构 + 主线 + 明日观察点 |
| 600111 筹码 | 2 次工具 → 642 字，结论 + 4 条依据 | 5 次工具 → 1430 字，筹码结构 + 逐笔 + 盘口 + 预案 |

同一只票、同一个问题，**配方版的证据维度明显更全**；默认版更依赖"系统摘要"这类二手结论。

代价：耗时从 10–20s 涨到 26–60s（最慢 60.6s 的竞价撤单率问题）。这类问题本来就重，
但意味着**配方不适合挂到 cron 批量跑**，只适合用户主动问。

## 四、暴露出的真问题

1. **结构合规不可测**：上表那列作废。要测"是否按配方段落作答"，得把 output_sections 作为期望集，
   并且**保存完整答案**（现在只存了前 160 字），否则无法复算。
2. **没有 trace**：工具调用数只能从 SSE 的 stage 事件数近似，拿不到"调了哪个工具、参数是什么、有没有被白名单拒绝"。
   这正是 L0 trace 要补的（`harness_runs.steps`）。
3. **成本可见但不可控**：60s 的问题没有预算提示；下一版应在回答尾部标注"本轮 N 次工具调用 / M 秒"，
   让用户自己判断要不要重问。

## 五、下一步（按价值排序）

1. **落 L0 trace**（工具级），否则所有优化都是盲调；
2. 回归集 30 条（含今天这两个 bug）+ 评分器；
3. 配方只保留 3 个先跑（盘前 / 风控 / 筹码），其余观察——**没有证据表明 6 个都值得维护**；
4. 给重配方加"预算提示 + 一键降档（转默认配方）"。
