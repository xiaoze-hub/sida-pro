## 1. 结论先行

- **今天能证明的链路（已接线、已测）**：用户确认 → `POST /copilot/actions/{id}/apply`（服务端按 `user_id` 过滤，非本人 400）→ 前端用 apply 响应拿到「动作 id / status=applied / payload 里的标的·标签·价位」→ 立刻 `GET /copilot/annotations` 回读 → 只有回读行与 apply 的 `label+price` 逐字对上（且 `source="ai"`）才画到真 K 线，图上带「服务端标注 #id + 确认动作 #id」。
- **今天不能证明、因此不做的事**：
  1. **刷新后无法证明"这条线来自哪次确认"** —— `KlineAnnotation` 没有 `action_id` 列，读取接口也不返回，故刷新后 provenance 只能显示"动作溯源不可用"，绝不从本地存储补一个 action id。
  2. **无法证明"这条线是我确认的"还是"全局共享行"** —— 读取接口返回 `user_id == 我 OR user_id IS NULL`，但响应不带 `user_id`/`scope`。因此**刷新时只画本会话确认过的标注 id**；服务端有行但本会话没确认过的，一律不画（状态带明说原因）。
  3. **撤销不可用** —— `rollback_action` 对 `kind="annotation"` 直接 400「annotation 动作不支持回滚」，也没有删除图注的接口。
- **不存在"本地对象当凭证"的路径**：旧 `saveOverlay` 恒拒（`client_authored_levels`），图元级旁路 `injectDecisionLevels` 仅接受由服务端响应解析并打标的数组，旧 `sida_kline_overlay:v2:*` 存储在代码里已不再读取。

## 3. 阻塞清单（每条都可复现，不是猜测）

### B1 图注没有 action 溯源（阻断"刷新后仍能证明来自确认"）
- 现象：`GET /copilot/annotations` 只有 `{id,price,ts,label,note,color,source,created_at}`。
- 根因：`KlineAnnotation` 表无 `action_id`；`_apply_annotation` 不知道动作 id（`apply_action` 调用时没传）。
- 影响：刷新/换标签页后，前端无法把一条线连回某次确认，只能降级显示"动作溯源不可用"。

### B2 图注归属不可区分（阻断"服务端有行就画"）
- 现象：响应里没有 `user_id`/`scope`；查询本身包含 `user_id IS NULL` 的全局行。
- 现状：当前代码库没有任何路径会以 `user_id=NULL` 写 AI 图注（`_apply_annotation` 强制写 `str(user_id)`），所以全局 AI 行只可能来自历史数据/人工 SQL；但这**不是契约保证**。
- 影响：一旦线上出现全局行，前端按"服务端有行"直接画，就会把别人的/历史的标注当成本人确认的结论。

### B3 撤销没有服务端入口
- 现象：`POST /copilot/actions/{id}/rollback` 对 annotation 返回 400；无 `DELETE /copilot/annotations/{id}`。
- 影响：用户确认错了价位，只能看着它在图上（本会话内），无法在服务端撤回；界面上只能如实写"撤销不可用"。

### B4 apply 不返回新建图注 id
- 现象：apply 响应是 `actions._to_dict(row)`，`result` 只有一句中文（"已标注 600111 @ 32.8：支撑位"），`db.add(row)` 后也没保留新行 id。
- 影响：确认那一刻必须靠 `label+price` 回读对账（已实现，且比"拿 apply 价位直接画"更硬），但如果服务端同一 tick 落了多条同价同标签的行（例如另一条 user 图注），对账会退化。

### B5 周期语义缺失（产品级）
- 现象：`propose_scenario_annotations` 不写 `period`，`_apply_annotation` 默认 `1d`；`apply` 也不接受视图周期。
- 影响：用户在 5 分钟图上看参谋结论、确认后，标注落在 `1d`，5m 视图上看不到（前端会如实提示周期不匹配，但这是产品缺口，不是前端能补的）。

## 4. 最小后端契约（按价值排序，每项都小）

1. **apply 回传新图注 id**（改动最小、收益最大）
   `_apply_annotation` 返回 `KlineAnnotation` 行（或 `apply_action` 里 `db.flush()` 后取 `row.id`），`_to_dict` 增加 `annotation_id`。前端即可把"对账"从 `label+price` 升级为 id 精确匹配。
2. **图注带上动作与归属**
   - `KlineAnnotation` 增列 `action_id INTEGER NULL`（FK `copilot_actions.id`），`_apply_annotation` 写入；
   - `GET /copilot/annotations` 响应行增加 `action_id`、`owner: "mine" | "global"`（由查询条件派生，不用泄露 user_id）、以及回显 `symbol/market/period`。
   前端据此可：刷新后仍显示"动作 #7"，且只画 `owner == "mine"` 的行。
3. **撤销**
   `DELETE /copilot/annotations/{id}`（`user_id` 过滤 + `AuditLog(action="copilot_annotation_delete")`），或让 `rollback_action` 支持 `annotation`（按 `action_id` 删行、写审计、`result` 里回 `deleted_annotation_ids`）。前端已留好 `rollbackPendingAction` 接线与文案位。
4. **视图周期透传**
   `propose_scenario_annotations(..., period=view.period)` + `apply` 时沿用 payload 的 `period`。否则 5m/60m 视图永远看不到情景标注。

在上述 1、2 落地前，前端**不会**把刷新后的行标成"已确认"，也不会画没有本会话确认凭证的行 —— 这是刻意的：宁可少画一条，不把别人的/历史的行为算成当前账号的确认。

**不变量**（都有测试）：
1. 本地价位（正文正则、罗盘、sessionStorage 历史行）永远不上图；
2. 未确认（只有 pending）永远读不到 ⇒ 不可能上图；
3. 画出的价位=服务端行的 `price`，标的/周期=本次请求键，类型由服务端 `label`/`color` 确定性映射；
4. 换账号/换标的/换周期三向隔离（客户端 id 信封 + 服务端 user_id 过滤双保险），且不跨账号清除；
5. 服务端删行 ⇒ 刷新不画 + 本地信封收敛；接口失败/形状不符 ⇒ 明确报错不猜。
