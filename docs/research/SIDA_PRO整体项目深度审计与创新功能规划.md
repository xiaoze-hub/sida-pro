### 0.2 三条最重要的判断

**判断一：这个项目的工程质量高于同类产品，但"能力密度"已经溢出"可用性密度"。**
419 个端点、39 个页面、54 个工具，而一级导航只有 6 组；大量能力存在但用户找不到，或被埋在一个从未被点开的 Tab 里（`get_exday_data` 的撤单量、`get_kzz_info` 的转债条款、`get_ipo_info` 的打新日历——**全部后端就绪、前端 0 消费**）。下一步的边际收益不在"再加功能"，而在"把已有能力接到用户手上"。

**判断二：最危险的不是单源依赖本身，而是"把数据缺失当成数据结论"。**
已定位一处 P0 级语义缺陷：`decision_pioneer.py` 里 `l2_inflow` 用 `available and zjl>0` 表达，当 TQ 网关抖动（`available=False`）时，一只 G 区 + 机构活跃度 5.0 的强势票会被判成 **"⚡ 警惕背离·主力出货"**。这不是显示错误，是**方向性误导**，而且该字符串本身还踩了全站合规词表（"主力出货"）。这条必须在 AI 数智参谋上线**之前**修掉，否则参谋卡第一天就会把"TQ 断线"讲成"主力在出货"。

**判断三：AI 数智参谋正在并行施工，但"前端已上线、后端未落地"，当前是带伤状态。**
工作树实测（`git status`）：`frontend/src/components/copilot/` 4 个组件、`hooks/useCopilotBrief.ts`、`pages/AiCopilot.tsx`、`src/agents/chat/tools_market.py`（5 个新工具）、`registry.py` 注册、`chat.py` 阶段文案**都已写入**，并且 `SuggestTab.tsx:159`、`StockWorkbench.tsx:463` 已经把它们挂到了生产页面上。但 `src/web/api/copilot.py` 与 `src/core/copilot_brief.py` **不存在**——`GET /api/copilot/brief/{symbol}` 与 `/api/copilot/presets` 都是 404。
后果：**个股工作台「建议」Tab 每只票都会渲染一次"参谋卡片暂时取不到数据"**（组件有错误兜底，不会白屏，但是可见的功能回退）。详见 §3.0。
同时，设计文档的三处前提需要修订：① CYQ 的 dict bars P0 **已在 v0.14.9 修复**（本文实测通过），文档仍列为"必须先修"；② `evidence.auction.volume_ratio` 实际来自 thsdk→TQ 逐票增强，可能为 `None`，caliber 串需改写；③ R2/R7 读 `resonance_warning`，而该字段会被 A-01 污染。**参谋层不能建在会撒谎的证据层上。**

三个结构性事实，直接决定后面的所有风险判断：

1. **TQ 网关是无状态薄 RPC，不支持回调**（`subscribe_hq` 不可用）。这意味着"实时"只能是**批量轮询**，而批量能力（`get_pricevol` 500 只/片）目前只被"涨跌家数"和"连板梯队"用到——**最大的性能红利没吃到**（→ I-1）。
2. **4 个 worker 各自持有一份进程内缓存**。`auction_pool._CACHE_TTL=30`、`chip_distribution._NEAR_CHIPS_TTL=3600`、`main_flow_compare._CACHE_TTL=30` 全部 ×4。所谓"30s 缓存"在 4 worker 下等于"每 30s 最多算 4 次"。
3. **thsdk 是 21 个模块的硬依赖**，竞价池、暗盘、问财、板块全部单源。thsdk 抖一次，竞价 + 暗盘 + 选股同时失血（§2.4）。

## 2. 深度审计：暗坑、断链与体验断层

编号规则：`A-xx` 一旦分配永不复用。级别沿用 `docs/KNOWN_ISSUES.md` 的定义（P0 数据错误/安全；P1 运行时可触达；P2 技术债/局部）。

### 2.1 P0 — 会产生错误结论或打垮上游

#### A-01【P0】L2 断链被判定为"主力出货"，并触发合规违禁词

**位置**：`src/core/decision_pioneer.py:633`、`:648`

```python
# :633
l2_inflow = l2_info.get("available") and (l2_info.get("zjl_hb") or 0.0) > 0
...
# :647-650
elif gs_zone in ("G", "G区", "G区间") and not l2_inflow:
    resonance_state = "⚡ 警惕背离·主力出货"
    resonance_action = "虽处G区但主力资金流出，提防主力假突破诱多出货"
```

**问题**：`l2_inflow` 是一个布尔值，但它承载了三种完全不同的语义 —— ① 真的净流出；② 数据不可用（TQ 网关超时/客户端未开/非交易时段会话值为 0）；③ `zjl_hb` 恰好等于 0。三种情况被压成同一个 `False`，然后走"资金流出"分支。

**影响面（这是它值 P0 的原因）**：

- 个股工作台 Band 的"铁三角共振"结论；
- `get_decision_pioneer` chat 工具（AI 会原样复述"主力出货"）；
- 全市场选股铁三角扫描（`resonance_scan`）——一只票被误判，整张榜的可信度归零；
- 即将上线的 AI 参谋卡 R2/R7 规则（设计文档 §4.9.1）直接读 `resonance_warning`，会把污染传播到"减仓/不参与"的操盘预案。

**叠加问题**：字符串 `"主力出货"` 命中全站合规禁用词表（设计文档 §1.4 明确列为禁用；`src/web/api/skills_gateway.py:236` 也是同一张表）。同一模块里 `resonance_action` 还写着"建议逢低重点关注""顺势持股"，属"建议"类表述，与 `trend_pilot_line.py:14`、`jbp_pool.py:17` 里"不含建议买入/卖出"的自律声明自相矛盾。

**修复方案（三态化，不接受折中）**：

```python
# 语义三态：True=净流入 / False=净流出 / None=不可判定
l2_dir = l2_info.get("direction")            # "净流入"/"净流出"/"平衡"
l2_inflow = True if l2_dir == "净流入" else (False if l2_dir == "净流出" else None)
l2_available = bool(l2_info.get("available"))

# 状态机：不可判定时不进"背离"分支，单独给"证据不足"态
elif gs_zone in ("G", "G区", "G区间") and l2_inflow is False:
    resonance_state = "⚡ 资金背离·上行承压"          # 去掉"主力出货"
elif gs_zone in ("G", "G区", "G区间") and l2_inflow is None:
    resonance_state = "— 资金维缺失·仅双指标"
    resonance_warning = "unknown"                     # 新增枚举，前端灰显
```

**必带回归测试**（`tests/test_decision_pioneer_resonance.py`，新增）：

| 用例 | 输入 | 断言 |
| :--- | :--- | :--- |
| L2 净流入 | `available=True, zjl_hb=+5000` | `resonance_state` 含"共振"，`warning != "warning"` |
| L2 净流出 | `available=True, zjl_hb=-5000` | `"资金背离"`，**不含**"主力出货" |
| **L2 不可用** | `available=False` | `warning == "unknown"`，且 `"背离" not in state`（本条锁死 P0） |
| 合规词表 | 全模块 | `re.search("主力建仓|主力出货|建议买入|建议卖出", 源码) is None` |

**工期**：0.5 d（含测试）。**必须在 AI 参谋 P0 批次之前合入。**

#### A-02【P0】竞价池 N+1 打穿单台 Windows 客户端

**位置**：`src/core/auction_pool.py:250-307`

```python
for r in all_records:                       # ← 池子约 1000 行（vendor docstring 自述）
    info = _rpc("get_more_info", {"stock_code": tq_code})   # ← 每票一次同步 JSON-RPC
```

**量化**：thsdk 竞价异动池单市场约 1000 行。每行一次 `get_more_info`（104 字段，单票接口，`packages/.../tq.py:475` 的 vendor 也是逐票循环）。按局域网 RPC 20–50 ms/次估算：**20–50 秒/次全量增强**。而：

- `_CACHE_TTL = 30.0`（`auction_pool.py:50`）——**缓存比计算还短**，等于几乎不缓存；
- 前端 30s 轮询（`AuctionAnomalyTab.tsx:124`）；
- 生产 `WEB_WORKERS=4`（`src/bootstrap/cli.py:24`），缓存不跨进程；
- 多用户同时在线时，每个 worker 各算一遍。

**峰值估算（口径要说准，否则会被当成夸张）**：

- **单次刷新**：约 1000 次单票 RPC，耗时 20–50 s；
- **单用户**：30 s 轮询 + 计算 20–50 s ⇒ 实际是"算完立刻再算"，**上游几乎 100% 占用**；
- **多 worker**：4 个 worker 缓存互不可见，4 个并发请求（4 个用户，或同一用户开 4 个标签页）就会让 4 份缓存同时失效 ⇒ **每 30 秒 4000 次 RPC**；
- **叠加**：这台 Windows 机器同时还要服务 K 线、盘口、批量选股、情绪序列、妖股因子。

**这不是"慢"，是把整个系统的数据源当沙包打。**

**修复方案（三步，缺一不可）**：

1. **降维**：五态研判真正需要的只有 `OpenZAF / OpenVolPre1 / OpenAmo / OpenZTBuy / BCancel+TotalBVol`。其中前三项在 thsdk 池子里已部分具备，`gap_pct` 已有。**先按"候选过滤"再增强**：只对 `gap_pct` 非空或 `open_amount` 缺失的前 200 行做 TQ 增强（Top-N 才是用户会看的），其余标 `enhanced=False`。
2. **批量**：`get_more_info` 只能单票，但 `get_pricevol` 支持 500 只/批（实测 587 码 84 ms，`tdx_boards.py:10`）。价格/量/涨幅维度全部走批量，仅"撤单/封单"这类必须单票的字段走 Top-N。
3. **单飞 + 跨进程缓存**：同一 key 加 Redis 锁（`panwatch-redis` 已在 compose 里），把 4 worker 收敛成 1 次计算；TTL 按阶段给：竞价窗口 5 s、盘中 15 s、收盘后 300 s、非交易日 3600 s。

**验收**：竞价池 P95 < 3 s；单次刷新 RPC 次数 < 250（可从 `tq_rpc_observability` 计数断言）。

**工期**：2 d。

### 3.3 参谋的差异化不该是"会说话"，而该是"说得清"

市面上的 AI 股票助手全都在拼"结论像人"。SIDA 的独占优势是**证据链完整**（筹码/撤单/量价/竞价/妖股/主线七块，每块都有单一事实源和口径串）。所以参谋卡的**第一卖点应该是"证据可信度"而不是"结论"**：

- 每个数字后面一个可点的 `ⓘ` → 弹出「来源 / 口径 / 数据时刻 / 是否降级」；
- 顶部一个 `证据 5/7` 的进度环，缺哪块、为什么缺，一眼可见；
- 结论区永远带 `rule_id`（R1–R9），点开显示"命中了哪条规则、哪几个条件"。

这三件事的成本很低（数据都现成），但**没有任何竞品做**——因为它们没有可追溯的证据层。这才是"降维"。

### 4.2 I-1 全市场 1 秒横截面雷达（Cross-Section Radar）

**为什么是降维**：所有股票软件的默认范式是"**个股分时**"——你盯 20 只自选，看它们的曲线。没有产品给你"**全市场在同一瞬间的横截面分布**"，因为那需要 5000 只 × 1 秒的数据吞吐。而 TQ 的 `get_pricevol` 实测 **587 码 / 84 ms**（`tdx_boards.py:10`），5000 只 ≈ **0.8 秒**——**这个能力就在那里，只被用来数涨跌家数**。

**数据基础（零新增依赖）**：
- `get_pricevol`（批量价量：现价/昨收/量/涨幅），500 只/片；
- `get_more_info`（仅对 Top-N 增强：委比/撤单/封单）；
- `get_stock_list`（全 A 码表，已有 `universe`）。

**算法/产品形态**：

1. **横截面快照**：每 1–3 秒一片，全 A 落一张宽表 `{symbol, price, chg, vol_ratio_1m, 涨速_3s, 板块}`。
2. **分位化**：每个指标在**当日全市场**的分位（P50/P90/P99）。"涨速 P99" 比 "涨速 1.2%" 有信息量得多——**绝对值的意义依赖分布**。
3. **异动聚类**：同一 3 秒窗口内，同板块 ≥3 只同时进 P95 → "板块级脉冲"，这是打板/接力最需要的信号，现有产品要等 30 秒后才在涨幅榜看到。
4. **UI 落位**：`/radar` 一级页（或工作台右上角常驻小窗）：
   - 左：全市场热力条（按分位着色，一眼看"钱在往哪流"）；
   - 中：`涨速 P99` 实时流（每秒滚动，带板块归属）；
   - 右：`板块脉冲` 卡片（"9:41:07 光模块 4 只同秒进 P95"）。
5. **与现有铁三角的关系**：铁三角是**日频结论**（T-1 15:30），雷达是**秒级事实**。两者互补：雷达发现"正在发生"，铁三角解释"为什么值得看"。

**护城河**：需要客户端级批量行情 + 无配额。竞品要复刻，得先买一份 L1 全市场推送（年费六位数）。

**风险/护栏**：
- 单台 Windows 客户端 CPU：5000 只/秒 × 104 字段不现实 → **只用 `get_pricevol` 的 4 字段**，`get_more_info` 只对触发 P95 的票补（每片 ≤20 次 RPC）；
- worker 竞争：雷达必须**独立进程/独立协程**跑，不能和 API 抢 RPC（否则 419 个端点一起变慢）；
- 数据只在内存环形缓冲（60 秒），不落库，避免写放大。

**MVP（5 天）**：`src/core/cross_section.py` + `/api/radar/snapshot`（GET，读内存）+ `/radar` 页 + 1 个 SSE/轮询。先只做"涨速 P99 流 + 板块脉冲"两件事，不做全指标。

### 4.3 I-3 委托行为画像：把"撤单率"从一个数变成一个坐标系

**为什么是降维**：现在所有产品（包括本项目的 `cancel_order_intent`）判断"诱多"用的都是**固定阈值**——"撤单率 > 40% = 诱多"。但 40% 对小盘票是常态，对茅台是异常。**同一个阈值用在 5000 只票上，必然一半误报。**

**关键发现（本次审计最有价值的一条）**：`get_exday_data` 提供**日线级**的 `BCancel/SCancel`（撤单量）+ `BOrder/SOrder`（委托量）+ 四档 `Amo/Vol` + `CJBS`（成交笔数），**且支持 `count` 回溯多日**。这意味着可以算出**每只票自己的历史撤单率分布**——而 `src/web/api/market_data.py:1503` 已经把它出参了，**前端 0 消费**（A-05）。

**算法**：

```
base_rate_i   = median(BCancel/(BOrder) over 近 60 交易日)      # 这只票的"常态撤单率"
z_i           = (today_rate - base_rate_i) / std(近60日)         # 今日偏离几个标准差
intent        = 固定阈值 → 分位判定：
                 z > 2 且 涨幅 > 3%   → 托单诱多（相对它自己的历史异常）
                 z < -1 且 跌幅 > 2%  → 抛压真实/恐慌确认
                 |z| < 1              → 常态（**不再误报**）
```

**产品形态（工作台"盘口资金"Tab 新增一块）**：

- 一条**撤单率时序带**（60 日），今日值用红点标出，旁边写 `P97（近 60 日）`；
- 一句话结论：`今日买撤 62%，为近 60 日 P97（常态 41%±9）—— 相对它自己异常，非绝对高位`；
- 跨股可比：同一个 `z` 值在 5000 只票之间可以排序 → 全市场"撤单异常 Top"榜（**这是新榜，现有产品没有**）。

**护城河 5/5**：`BCancel` 是 TQ 独有字段，东财/腾讯免费层完全拿不到（`market_data.py:1502` 注释已实测确认：`002361 BCancel=194573`）。

**工期**：1 天接线（A-05）+ 2 天算法与 UI = **3 天**。这是全表里性价比最高的一项。

### 4.4 I-2 用户公式云 + 公式市场（战略级，护城河最高）

**核心洞察**：通达信用户最舍不得的不是行情，是**自己写了十几年的公式**。目前这个资产只能在本机跑、只能手动跑、只能自己看。**没有任何云端产品能承接它。**

**而且我们已经有 80% 的引擎了**（这是本条能从"构想"变成"8 天 MVP"的原因）：

1. `formula_scan` / `formula_process_mul_xg`：**服务端全市场执行条件选股公式**，实测 5577 只 / 24.2 秒（`tq.py:1750`）；
2. `formula_process_mul_zb`：批量指标公式（500 只/批，筹码/均线/自定义指标）；
3. `tq_formula_signal_scheduler`：每日 15:50 定时 + 交易日历 + 10 日回补（已生产跑了 108 个内置公式）；
4. 已有的 10+ 渠道推送 + 多租户 RBAC + 影子账户（可做"公式绩效账本"）。

**缺的只有两样**：① 让用户把自己的公式填进来（校验 + 存储 + 归属）；② 一个能看结果的界面。**引擎不用重写。**

**产品三段**：

| 阶段 | 能力 | 用户价值 | 工期 |
| :--- | :--- | :--- | :--- |
| **P1 我的公式** | 粘贴通达信公式源码 → 语法校验 → 保存为"我的策略" → 每日 9:25/14:50 云端全市场跑 → 命中推微信 | "我的公式终于能自动盯盘了" | 8 d |
| **P2 公式回测** | 用历史 K 线回放公式（已有 `backtest/` 与 `factor_ic` 基建），输出命中率/次日溢价/最大回撤 | "这个公式到底行不行" | 8 d |
| **P3 公式市场** | 公式分享/订阅/绩效榜（真实回测数据背书，不可刷） | 内容生态 + 抽成 | 15 d |

**为什么这是护城河 5/5**：迁移成本是**资产级**的。用户一旦把 20 个自编公式放在这里，换产品 = 重写 20 个公式 + 重跑历史。而同花顺"问财"是自然语言（不支持自编公式），通达信客户端支持公式（不能云端定时+推送）。**中间这个缺口，只有我们站着。**

**风险（必须提前想清楚）**：
- **公式沙箱**：绝不能让用户公式在服务端执行任意代码。TQ 的 `formula_process_mul_xg` 是把公式**发给客户端**执行，天然隔离——这是安全的关键，务必坚持这条路径，**不要**自己在 Python 里解释公式；
- **算力**：全市场 × N 个用户 × N 个公式。用"公式去重 + 结果共享"：同一公式文本 hash 相同 → 只跑一次，结果按用户分发；
- **合规**：公式市场若出现"必涨公式"，平台要担责 → 上架审核 + 强制回测数据披露 + 免责声明（复用 `skills_gateway` 的合规词表）。

### 4.5 I-4 转债-正股联动套利雷达

**现状**：`get_kzz_info` 一次返回 **14 个字段**（`registry.py:1588-1595` 实测）：`ZGPrice` 转股价、`CurRate` 当期利率、`RestScope` 剩余规模、`ForceRedeem` **强赎触发价**、`PutBack` 回售触发价、`ZGDate` 转股日、`EndDate` 到期日、`EndPrice` 到期价、**`RealValue` 纯债价值**、`HSScore` 评级 —— 条款数据**一个不缺**；`get_thsdk_market_data_bond` 有转债行情。**两样都有，没有任何页面。**

**产品逻辑（把转债做成"正股事件的二阶导数"）**：

```
转股价值 = 100 / 转股价 × 正股现价
溢价率   = 转债价 / 转股价值 - 1
双低值   = 转债价 + 溢价率×100
强赎距离 = (正股价 - 强赎触发价) / 强赎触发价
纯债溢价 = 转债价 / RealValue - 1        ← 纯债价值直接取 TQ，不用自己贴贴现率
```

> 注意：`RealValue`/`ForceRedeem` 由客户端给，**不要自己按 3.5% 贴现率估算** —— 一旦和客户端数字不同，又回到 A-06 的信任问题。

**四个可交易的场景（每个都是一个卡片）**：

| 场景 | 触发条件 | 用户动作 | 为什么别人做不到 |
| :--- | :--- | :--- | :--- |
| **正股涨停 → 转债滞后** | 正股封板 + 转债涨幅 < 转股价值涨幅 - 3% | 转债补涨博弈 | 需要正股封板状态（`zdt_snapshot`）+ 转债实时 + 转股价，三源合一 |
| **强赎倒计时** | 正股 ≥ 强赎触发价 且 剩余天数 < 15 | 转股 or 卖出（强赎是硬约束） | 条款数据在 TQ，免费源没有 |
| **双低轮动** | 全市场转债按双低值排序，取 Top20，每周调仓 | 低风险增强 | 需要全市场转债 + 正股 + 条款 |
| **折价套利** | 溢价率 < -1%（转股即赚） | 转股套利 | 需要实时 IOPV 等价物 |

**工期**：6 天（数据聚合 3 d + 4 张卡 3 d）。**建议先做"强赎倒计时"单卡**（1.5 d），它是最刚性的需求（错过强赎直接亏 30%）。

### 4.6 I-6 筹码迁移电影 + 全市场吸筹完成度榜

### 4.7 I-5 ETF 折溢价 → 权重股传导链（小创新，快）

**工期**：2 天（`get_trackzs_etf_info` 已有 `Zgb/Sz` 份额字段，权重需一次静态配置）。

### 4.8 I-7 竞价三阶段解剖（二期，但概念最强）

**现状**：竞价页只给 9:25 的**快照**（一个时点的池子）。而竞价真正的信息在**过程**：9:15–9:20 可撤期挂了多少、撤了多少；9:20–9:25 不可撤期还剩多少（**剩下的才是真金**）。

**做法**：竞价窗口内每 15 秒采样一次全市场竞价量（`get_pricevol` 批量，成本极低），落一张 `auction_tape` 表；9:25 后计算：

```
虚单率 = (9:20 时挂单量 - 9:25 时挂单量) / 9:20 时挂单量
真金率 = 1 - 虚单率
```

**产品**：每只票一条"竞价心电图"（三次采样的量柱），外加"9:19:5x 集中撤单"标记（这类精确到秒的剧本，散户从来没见过）。

**工期**：4 天（采样器 2 d + UI 2 d）。**依赖 A-02 先修**（采样器和竞价池会抢 RPC）。

## 6. 工程与治理建议

### 6.1 性能

| 项 | 现状 | 建议 |
| :--- | :--- | :--- |
| 批量能力 | `get_pricevol` 只被 2 个模块用 | 所有"多标的同字段"场景一律批量（竞价、雷达、涨跌停、板块） |
| 缓存 | 进程内 ×4 worker | Redis + 单飞；key 带 `phase`（竞价/盘中/收盘/非交易日） |
| 冷启动 | `/ladder` 曾 6.5s（已预计算） | 把"预计算 + 快照表"变成默认范式，禁止"每次请求现算全市场" |
| 上游保护 | 无 | 给 TQ 加**令牌桶**（全局 QPS 上限）+ 排队超时，防止某个新功能打穿客户端 |

### 6.2 权限

- 页面守卫与 API 权限**必须同源**（A-04）。建议生成一张"路由 → 权限点"映射表放 `src/core/permissions.py`，前后端共用一份（前端从 `/api/me/perms` 拿，不再手写 `perm="..."`）。
- `gated`（权限不足）/ `degraded`（数据缺失）/ `empty`（真无数据）三种语义必须在 API 层就分开（设计文档 §4.6 已定义，推广到所有端点）。

### 6.3 合规

- 词表门禁从 `copy.ts` 扩到 `src/**/*.py` + chat system prompt + 通知模板（现在 `decision_pioneer.py:648` 与 `resonance.py:126` 都在裸奔）；
- 所有"方向性结论"必须能追溯到 `rule_id`——这既是合规要求，也是产品卖点（§3.3）。

### 6.4 可观测

补齐四个指标，就能提前发现 A-01/A-02 这类问题：

1. `tq_rpc_total{method, ok}` —— 打穿客户端前会先在这里看到尖峰；
2. `evidence_degraded_total{block}` —— 哪块证据在频繁断（参谋卡的可信度直接相关）；
3. `verdict_unknown_total{module}` —— "证据不足"占比，突增说明上游挂了；
4. `as_of_lag_seconds{endpoint}` —— 数据陈旧度（A-03 的量化版）。
