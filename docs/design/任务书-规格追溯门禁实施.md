## 1. 硬约束（违反即返工）

### 1.1 环境：必须清 PYTHONPATH

本机 Hermes 的 `PYTHONPATH` 指向 Python 3.14 的 site-packages，会污染项目 3.11/3.12 环境，
导致 `pydantic_core._pydantic_core` 找不到。**所有 pytest 命令必须这样跑**：

```bash
cd /home/ubuntu/sida-pro
env -u PYTHONPATH -u VIRTUAL_ENV .venv/bin/python -m pytest tests/test_spec_*.py -q -p no:cacheprovider
```

用错环境的报错长这样（看到就是这个坑）：
```
ModuleNotFoundError: No module named 'pydantic_core._pydantic_core'
```

### 1.2 规格数量必须以**运行时实测**为准，不能抄文档

我在写规格时抄了旧文档的「59 个工具」，门禁立刻报 `代码 64 个, specs 声明 58 个`。
**实际数据（已核对）**：

| 名字 | 含义 | 数量 |
|---|---|---|
| `CHAT_TOOL_REGISTRY` | 注册表本体（name → ChatTool） | **66** |
| `chat_tool_schemas()` | 对模型可见（有 schema 的） | **64** |
| handler-only | 有 handler 但 `schema is None`，不暴露模型 | **2** |

handler-only 的两个：`get_opportunities`、`note_new_dimension`。

> ⚠️ **口径差异**：`CHAT_TOOLS` 在 `src/web/api/chat.py`（= `chat_tool_schemas()`），
> 不是 `src/agents/chat/registry.py`。而 **caliber / requires 只在 `ChatTool` 对象上**，
> schema 导出后这两个字段就没了 —— 所以守 caliber 必须用 `CHAT_TOOL_REGISTRY`，
> 守 schema 数量才用 `chat_tool_schemas()`。**别搞混。**

### 1.3 规格描述的是**行为契约**，不是实现

反例（不合格）：
```markdown
- **TOOL-005** get_capital_flow 调用 _tool_get_capital_flow
```
正例（合格）：
```markdown
- **TOOL-002** get_capital_flow 的 caliber 必须包含「禁止据此判定主力意图」红线
```

**判据**：删掉这个测试，会漏掉哪个 bug？答不上来就别写。

### 1.4 不改业务代码

本方案是**旁路**：门禁只读 `specs/` 和 `tests/`，不进生产链路。
**不要为了让门禁过而改 `registry.py` 或任何业务代码** —— 那说明规格写错了，改规格。

（唯一的例外：如果门禁发现的是**真 bug**，比如某工具 caliber 确实是空的，
那就修代码，但**要在 PR 描述里单独说明**，不要混在规格工作里。）

### 1.5 CI 走 push/PR，不是 schedule

`spec-gate.yml` 已配好 `push` + `pull_request`。**不要改成 schedule** ——
schedule 是事后发现，push 才是事前拦截。action 必须 pin SHA（本仓风格）。

## 2. 待办清单（按优先级）

### P1 · 11 个 harness recipe 的验收标准

**现状**：`src/harness/recipes/` 有 11 个 YAML
（`premarket_strategist` / `auction_hunter` / `chip_analyst` / `deep_diagnosis` /
`demon_diagnosis` / `intraday_analyst` / `intraday_watcher` / `left_diagnosis` /
`postmarket_reviewer` / `risk_judge` / `theme_leader`）。

**做法**：
1. 为每个 recipe 建 `specs/harness/<id>.md`，先只写 **2-3 条**最核心的标准，不要一上来写全
2. 标准 ID 用 `RECIPE-001` 起（recipe 之间**不要重号**，建议每个 recipe 独立前缀段：
   `RECIPE-PM-001` / `RECIPE-AH-001`…，或者统一递增但要保证唯一）
3. 建 `tests/test_spec_harness_recipes.py`，每个 recipe 至少 2 个守卫测试
4. **通用守卫优先**（一次写好覆盖 11 个 recipe，收益最大）：

```python
def test_every_recipe_declares_acceptance():
    """@spec RECIPE-001
    每个 recipe 必须声明 acceptance(至少 1 条), 且 acceptance 条数与 specs 一致。
    """
    # 遍历 src/harness/recipes/*.yaml, 对照 specs/harness/*.md

def test_recipe_output_sections_are_respected():
    """@spec RECIPE-002
    recipe 的 prompt_fragment 必须声明全部 output_sections 段落名, 原文照抄。
    """
    # 静态检查 prompt_fragment 里是否出现每个 output_sections 名字

def test_recipe_budget_is_declared():
    """@spec RECIPE-003
    每个 recipe 必须声明 budget.max_tool_calls。
    """
```

**注意**：recipe YAML 里还没有 `acceptance:` 段，需要**新增这个字段**（YAML 扩展，不影响运行逻辑）。
`src/harness/recipes.py` 负责加载，要确认它**不会因为多了字段而报错**（多半不会，但要验证）。

### P2 · 数据口径标准

**现状**：`src/harness/data_catalog.yaml` 已有雏形，正好接上。

建议的 3 条（先挑最痛的）：
```
DATA-001  get_capital_flow 返回的是第三方估算, caliber 必须标注(不得被表述为机构持仓)
DATA-002  主力意图必须走 get_main_intent(逐笔), 不得用 get_capital_flow 替代
DATA-003  K线基准日滞后时 UI 必须显式标注, 不得改数据
```

**DATA-002 的守卫怎么写**：`get_main_intent` 是唯一合法的"主力意图"出口。
守卫可以查：`_tool_get_capital_flow` 的返回里**不含**主力意图相关字段，
或者查 intent 相关的 handler 一定走逐笔接口。**先读代码再定断言，不要凭空写。**

### P2 · schema 一致性（可选，最费劲）

检查工具返回结构与 `specs/schemas/tool_contract.schema.json` 一致。
**这个最容易做偏，建议放到最后**，甚至可以不做。

## 3. 方案二：自举闸门（P2，可延后）

借鉴 self-hosting-agent 的 `src/orchestrator/client-source.ts`。

**三条规矩**（照搬）：
```
1. 只能改白名单目录 —— 内核不可被被监管者改写
2. 改完必须过自检, 不过就逐字节回滚
3. 每次成功变更留版本、留 diff、留审计
```

**映射到 SIDA-Pro**：
| 白名单（可改） | 禁改（内核） |
|---|---|
| `src/harness/recipes/` | `src/agents/` |
| `src/harness/skills/` | `src/core/` |
| recipe YAML | `src/harness/trace.py` |
| | `src/harness/selfmod.py`（自己） |

**明确不做**（重要）：
```
❌ 不允许自动改 SYSTEM_PROMPT / guardrails / 交易红线
❌ 不允许自动合并到主干 —— 产出只是「建议 + diff」, 合不合并由人决定
❌ 不借鉴 self-hosting-agent 的「自动生效」—— 那是客户端场景,
   我们是金融决策系统, 自动生效的爆炸半径太大
```

**只借鉴「改完能回滚」和「留 diff 留审计」。**

实现要点（都是那个项目踩出来的）：
- **逐字节回滚**：存 `previous_content` 字节流，不用 git checkout（可能有未提交改动）
- **回滚也记审计**：否则"回滚→重启→回滚失效"
- **自检失败不留半个文件**：先跑自检再落盘，或临时文件 + 原子 rename
- **路径校验在动磁盘之前完成**：绝对路径 / 盘符 / `..` / 符号链接全拒

## 6. 给执行 AI 的提醒

**这个任务最容易失败的方式，是把规格写成"给测试看的作文"。**

判据很简单：**每条规格都要能回答"删了这个测试，会漏掉哪个 bug？"**
答不上来的规格就删掉，别凑数 —— 因为规格数量本身不是 KPI，**覆盖到真承诺**才是。

另外一个坑：**门禁自己骗人比没有门禁更危险**。
self-hosting-agent 的源码注释里专门记了这个事故：

> 自检：某个规格文件一条验收标准都没识别出来，多半是 ID 命名超出正则（历史上就发生过）
> 于是整条规格对门禁隐形、还报「全部覆盖」

所以 `trace_specs.py` 里那条"每个规格文件至少识别出 1 条标准"的**自检必须保留**，
不要为了少写规格而放宽它。
