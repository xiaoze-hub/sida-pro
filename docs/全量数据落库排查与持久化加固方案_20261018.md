## 2. 审计口径：五级判定 + 二维评级

### 2.1 存储分层（沿用 20260910 设计文档词汇，避免二次发明）

| 层 | 载体 | 生命周期 | 可回测 | 本文判定 |
|---|---|---|---|---|
| **L0** | PG / TimescaleDB 结构化表 | 长期（分区+压缩+保留） | ✅ | **已落库** |
| **L0-KV** | PG `summary_cache` / `decision_cache` | TTL（7 天清理） | ❌ | **伪落库**（本文重点批判对象） |
| **L1** | Redis（`biz_cache`）+ 进程内 `TTLCache` | 秒~小时 | ❌ | **仅缓存** |
| **L2** | `DiskCache`（`/app/data/cache/*.json`） | TTL，重启回血 | ❌（覆盖写） | **仅缓存** |
| **L3** | 请求期直取，无任何留存 | 请求结束即消失 | ❌ | **瞬态** |

### 2.2 五类判定

- **A 已落库**：有表、有后台写入者、有唯一键、可查询区间。
- **B 覆盖不足**：表在，但只覆盖"自选∪持仓"或 Top-N（如 `quote_snapshots` 只覆盖自选+指数，`chip_daily` 只覆盖被查询过的票）。
- **C 过程丢失**：表在，但**覆盖式写入/滚动窗**把过程压成一个终值（盘口 5 帧、竞价终值、筹码日终）。
- **D 仅缓存**：无表，只有 TTL 缓存或 KV 表。
- **E 合理瞬态**：探测/联想/健康检查/一次性问财筛选——不落库是**正确**的，需显式列入白名单防止后人"补错"。

### 2.3 二维评级（决定优先级）

```
回测价值 高 ┌──────────────────────┬──────────────────────┐
           │ P1 补建（成本中等）    │ P0 立即补建（成本低）  │
           │ 两融/股东/分红/北向    │ more_info/竞价过程/   │
           │ 新闻归档/板块成分 SCD2 │ 转债/指数日K          │
           ├──────────────────────┼──────────────────────┤
           │ 不做（白名单）         │ P2 缓存 + 研究型表     │
           │ probe/联想/问财筛选    │ 热榜/异动/公司简介/盘口 │
           └──────────────────────┴──────────────────────┘
             加载影响 低              加载影响 高
```

## 5. 未落库原因深度归因（不是"偷懒"，是 5 种不同的工程惯性）

### 5.1 类型一：覆盖式写入 —— "存了，但把过程压成了结果"（危害最大）

**证据链**

- `src/core/orderbook_snapshot.py:41` `_WINDOW = 5`；`:239` `frames = frames[-_WINDOW:]`；
  `:240-251` 以 `symbol` 为键 `upsert` 一行、`payload` 存 5 帧 JSON。
  → 每 20s 采一帧，**第 6 帧进来时第 1 帧已永久消失**。20 档只留 10 档（`:44`）。
  → 后果：盘口演变（托单堆积/压单增厚/撤单/幽灵单）**只能看最近 100 秒**，无法复盘"9:45 那波托单是怎么堆起来的"。
- `auction_snapshots` 唯一键 `(trade_date, symbol, market)`，注释写明"竞价在 9:15-9:25 唯一 → 重跑覆盖"。
  → 该假设**只在"结果"维度成立**：竞价过程（试盘价、虚假封单、9:20 前撤单）恰恰是**分时变化的**，被"唯一"二字抹掉了。
- `chip_daily` 唯一键 `(trade_date, symbol, market)` → 一天一行，筹码**迁移过程**（峰位从 12.3 挪到 11.8）不可见。

**为什么当时这么写**：模块的第一需求是"请求端别再卡 12s"（`orderbook_snapshot.py` docstring 明说），
缓存语义天然是"覆盖"，于是把"缓存表"当成了"历史表"。**这是"表名带 snapshots，语义是 cache"的经典错位。**

**修复不需要新表结构革命**：同一份采集代码，把 `upsert 一行滚动窗` 改成 `append 一帧`，
保留期到点 `DROP PARTITION`。写入量增加 5 倍（40 只 × 720 帧/日 = 2.9 万行/日，仍是小数）。

### 5.2 类型二：只有终值，没有过程（竞价）

`src/agents/auction_review.py:75,88` 取快照时 `limit=20` / `limit=10`，`:102` 才落库；
且整段逻辑包在 `if not _has_wudao_only:` 里——**悟道可用时反而不落 TQ 快照**。
→ 结果：`auction_snapshots` 的实际覆盖 = "auction_review agent 跑过的日子里，自选前 20 只"。
生产上大概率是**几十天 × 十几只**，做竞价策略回测时样本量根本不够。

**归因**：落库被当成 agent 的"副作用"，而不是采集器的"职责"。正确做法是**独立采样 job**（09:15-09:25 每分钟一帧，全市场）。

### 5.3 类型三：请求期直取 + 进程内 TTL（"秒开"的头号敌人）

| 端点 | 缓存 | 冷启动代价 | 证据 |
|---|---|---|---|
| `/api/market-data/anomalies` | **无** | 东财一页 | `market_data.py:1562` 直接 `vendor.fetch` |
| `/api/market-data/hot-stocks` | **无** | 同花顺一页 | `market_data.py:1608` |
| `/api/thsdk-extended/{11 个}` | 仅 DDE 30s | thsdk 单并发，实际 1~8s | `thsdk_extended.py:63` `_DDE_TTL` |
| `/api/quotes/{symbol}/company` | 1h 进程内 | 智兔 1.8s | `quotes.py:253-254` |
| `/api/quotes/minute/{symbol}` | 60s 进程内 | 腾讯 + swings ≈ 15s | `quotes.py:357` |
| `/api/boards/{code}/constituents` | 1h 进程内 | thsdk | `thsdk_board.py:47` |
| `/api/market/indices` | 60s + 30min(spark) | 6×指数K，串行 ~4s | `market.py:36,42` |
| 转债雷达 | Redis 60s + 条款 12h | 冷启动 N 次 `kzz_info` | `cb_radar.py:39-40` |

**归因**：这些端点的作者都做了"缓存"，但缓存是**进程内**的——
`WEB_WORKERS=2` 时两个 worker 各存一份、重启即失、容器迁移即失。20260910 文档已把 `TTLCache→Redis` 列为批次 1，
但**只改了 marketdata 包**（`md_redis_cache`），**没改 API 层的私有 dict**。这是"改造做了一半"。

**更关键的是**：即使是 Redis，**也只解决"快"，不解决"历史"**。用户诉求 ① 回测，Redis 一点忙都帮不上。

### 5.4 类型四：用"通用 KV 表"冒充结构化落库

- `summary_cache`（`src/core/summary_cache.py`）：`(symbol, market, computed_at, ttl_s, payload TEXT)`，
  **7 天保留、按 TTL 判过期、payload 是 JSON 字符串**。
  承载：`fundamentals-detail`（龙虎榜+两融+股东+分红+公告+exday，`market_data.py:1535`）。
  → 不能按 `trade_date` 扫描、不能 join、不能算 IC、过期即删。
- `biz_cache`（Redis）：承载转债雷达、发现页、热榜、涨跌分布。
- `DiskCache`（`/app/data/cache/*.json`）：承载逐笔、筹码。`dark_flow_sampler.py:24-25` 明文写"**不落库**"。

**归因**：这三种载体的共同优点是"改一行代码就能用"，共同的缺陷是"**没有 schema**"。
一旦要回测，就得先写一个 ETL 把 JSON 抠出来——而那时 TTL 早过了。

### 5.5 类型五：合理瞬态（必须列入白名单，防止后人乱补）

`probe`（连通性探测）、`search_symbol`（联想）、`wencai`（条件筛选）、WS 推送、健康度 EWMA。
这些**没有历史价值**（可随时重算或本来就无意义），落库只会增加写放大与磁盘。
→ 建议在 `docs/` 与 CI 检查中各留一份白名单，新增端点若命中"无表 + 请求期直取"，必须在 PR 里说明归属哪一类。

## 7. 加固方案

### 7.1 五条硬原则（沿用仓库既有铁律，不新发明）

1. **写库只在后台**：API 层只读；请求期最多"读库 miss → 回源 → **异步**落库"（`price_distribution_store.get_or_refresh` 已是此形）。
2. **幂等**：全部 `ON CONFLICT DO UPDATE`，唯一键含业务时间，支持按 `(symbol, 日期区间)` 重放补数。
3. **口径列**：每表必带 `source`；派生值必带 `quality_flag`/`caliber`。**禁止跨源混算**（`klines.source` 已有先例）。
4. **零值不冒充**：缺失写 `NULL`；"全 0"不落库（`l2_fund_snapshot.has_live_values` 已有先例）。
5. **保留期即契约**：建表时同时定 `retention`，并在同一迁移里写注释；大表按 `trade_date` 分区/hypertable。

### 7.7 读路径改造模板（照抄 `price_distribution_store`）

```python
def get_or_refresh(symbol, market, *, ttl_s=None, refresh=False):
    if not refresh:
        row = load_latest(symbol, market)          # ① L0 读库
        if row and age(row) <= (ttl_s or default_ttl()):
            return {**row, "cache": {"hit": True, "source": "db"}}
    try:
        payload = fetch_from_vendor(symbol, market) # ② 回源
    except Exception as e:
        if row:
            return {**row, "cache": {"hit": True, "stale": True,
                                     "reason": f"{type(e).__name__}: {e}"}}
        return {"available": False, "reason": str(e)}
    upsert(payload)                                 # ③ 写穿（同事务内幂等）
    return {**payload, "cache": {"hit": False, "source": "live"}}
```

**关键点**：回源失败时**回吐旧行并标 `stale`**，绝不返回 0 或估算值——
这与仓库既有"降级诚实"铁律一致（`price_distribution.py:16`、`cb_radar.py` docstring）。

SELECT relname, pg_size_pretty(pg_total_relation_size(relid)) AS total,

SELECT count(*) FROM (

  ON m.symbol = s.symbol AND m.trade_date = CURRENT_DATE
