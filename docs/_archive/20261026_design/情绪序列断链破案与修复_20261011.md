## 1. 现象

`market_sentiment_daily`(TQ `get_scjy_value` SC01-35 全量落库)**停在 2026-09-22**;
而决策账本 `decision_log` 的信号到 **2026-09-25 之后仍在产**。后果: 情绪温度计/regime 取不到
信号当日的市场温度, 「胜率分桶验证」直接卡在「信号日无当日温度」(见
`docs/research/情绪温度计条件化与胜率证据_20261011.md` §4-3)。

属**「断链无人知」**类: 数据停了 19 天, 无告警、无自检、无人发现。

## 2. 破案(为什么停在 0922)

**不是「没接线」。** 同步入口**已在**生产调度体系里:

- 采集器 = `src/collectors/tq_sentiment_series.py`(TQ `get_scjy_value`);
- 调度器 = `src/core/tq_sentiment_scheduler.py`(`TqSentimentScheduler`, 每交易日 15:35,
  独立 `AsyncIOScheduler`), 由 `src/bootstrap/startup.py`(lifespan, 选主后)在 v0.13.4
  (`09bd122`, 2026-09-23 17:35)起**接线并启动**, 有单测 `tests/test_tq_sentiment_scheduler.py` 锁定;
- 另有手动入口 `POST /api/market/sentiment/sync`。

真正的机制是**失败与断链都不外显**, 三处叠加:

1. **每日同步失败被吞成一条日志**: `sync_sentiment_series` 把 TQ 异常 `except` 成
   `{"error": ...}`(仅 `logger.warning`), 调度器 `_sync_in_job` 也只 `logger.info/warning`
   → 跑没跑成、跑到哪, **作业面板与告警通道都看不到**。
2. **没有「表新鲜度」自检**: `data_quality_sentinel` 的 `tq_gateway` 检查(2026-10-08 加的)
   只探「网关**可不可达**」, **不校验 `market_sentiment_daily` 的 `MAX(trade_date)`** ——
   网关活但数据不更新(或某天取数失败)时哨兵**照样 ok**。这就是「断链无人知」的根。
3. **启动回补只在表近空时触发**: `_needs_backfill` 只在 `COUNT(*) < 30` 时补 420 天;
   表已有 ~282 行后, **中途断一次就永久停在断点**, 重启也不会自愈。

**直接触发**(无法在本机定论, 见 §4): TQ 链路在生产反复失联/未更新客户端 ——
`git log` 可见同期事故 `aea7ff0`(2026-09-27「国内数据网关整机失联」)、
`4b9f49d`(2026-10-08「TQ 断链 3 天无人发现」)。`tq.py` 头部亦记有
「TdxW.exe 未更新时 TQ 网关返回旧快照却报成功」的先例(该防护**只覆盖 K 线, 未覆盖 SC 序列**)。

## 3. 修复(本分支)

1. **每日同步接线加固 + 重试/降级诚实**: `sync_sentiment_series` 增 `retries`(默认 0, 零破坏),
   `TqSentimentScheduler` 每日同步给 2 次重试, 失败显式记 `ERROR`(不再静默)。
2. **新增 `src/core/sentiment_freshness.py`(仿 `ladder_freshness` 模式)**: 每日收盘后比对
   `market_sentiment_daily` 最新交易日 vs 期望交易日, 缺则 TQ 直连**批量**补数(带重试, 失败
   **显式**计数/留痕), 复检; 仍缺 → 作业按 `ok=False` 判 failed **+ 写通知(断链显式告警)**。
   接线于 `startup.py` 每日 **16:20**(与 TQ 类 15:35/15:50、全市场日线 16:00、连板自检 16:05、
   跨源标定 16:10 错开 —— TQ 单客户端进程)。
3. **补历史断档**: 一键脚本 `scripts/backfill_sentiment_series.py`(本地/生产可跑, 补后打印
   `MAX(date)` 前进); 与每日自检自愈同一实现。
4. **消费方陈旧标注(不拿旧值冒充当日)**: `derive_thermometer` / `current_thermometer` 增
   `stale` / `stale_days` / `expected_asof` 与「数据停在 X 日」说明; `market_regime.temperature_policy`
   遇 `stale` **不据此条件化**并显式标注; `GET /api/market/sentiment/health|baseline` 带
   `stale`/`expected`/`stale_days`。

## 4. 实补执行情况与阻塞(诚实记录)

本机(沙箱)**无法连 TQ 网关** —— 无 `TDX_QUANT_URL`, 候选探测预算耗尽(实测
「TQ 网关候选探测未在预算内完成(已探 2/12)且未配置 TDX_QUANT_URL」); 亦无法连生产 PG。
故 **2026-09-23 至今的真实补数未能在本环境执行**, `MAX(date)` 未前进。

已用**临时 sqlite + 真补数路径**验证链路正确性(禁改真值): 对停在 `20260922` 的表,
`check` 正确判出缺口 `20260923…20261009`(7 个交易日)、`stale=True`; `backfill_missing`
对真 TQ 发起调用 → 因网关不可达**显式失败**(`ok=False, attempts=2, error="TQ 网关不可用: …"`),
`MAX(date)` 保持 `20260922` —— 即「**失败显式、不静默、不伪造**」符合预期。

**待办(需能连 TQ 的环境)**: 在本地/生产执行
`python scripts/backfill_sentiment_series.py`(或等 16:20 自检自愈), 然后确认
`MAX(trade_date)` 前进到最近交易日、`/api/market/sentiment/health` 的 `stale=False`。

## 5. 口径与诚实声明

- 缺口枚举按**真实交易日历**(`ladder_freshness` 单一事实源, 交易日历且非周末); 空表不冒充「无缺口」。
- 补数/同步失败一律**显式**(`ok=False` + `error` + 尝试次数), 不用 0 或旧值冒充; 只有真取到并
  落库才算成功。
- 消费方数据陈旧时**显式标注**且**不据此条件化**, 不拿旧值充当当日。
